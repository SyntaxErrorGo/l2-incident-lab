# Сценарии инцидентов

| Режим | Уровень сбоя | Поведение | Главное доказательство |
|---|---|---|---|
| `normal` | Нет | FastAPI сохраняет заказ и возвращает 201 | Строка PostgreSQL и успешное событие backend |
| `bad_gateway` | Nginx/upstream | Только `POST /api/orders` уходит на недоступный адрес | 502 Nginx; POST отсутствует в backend |
| `slow_api` | Граница таймаута | Backend ждёт 8 с, а Nginx — 3 с | 504 Nginx и возможный поздний commit |
| `rate_limited` | Политика FastAPI | Ответ 429 с `Retry-After: 30` | Warning backend и заголовок ответа |
| `api_error` | Приложение FastAPI | Имитация ошибки возвращает 500 до записи в БД | Ошибка backend; заказа нет |
| `invalid_status` | Бизнес-данные | HTTP успешен, но сохраняется статус `UNKNOWN` | Строка PostgreSQL с неверным статусом |

## Чему учит каждый сценарий

- **502:** отделять доступность upstream от общего здоровья backend.
- **504:** не считать клиентский таймаут гарантированным откатом операции.
- **429:** ограничивать повторы и соблюдать указанный сервером backoff.
- **500:** коррелировать ответ с логами backend перед эскалацией.
- **Invalid status:** разделять транспортный и бизнес-результат.

Сброс через интерфейс или командой:

```bash
curl -i -X POST http://localhost:8080/api/incidents/reset
```
